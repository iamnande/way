# PRD — way craft pillar: Craft (discipline) + session log

## Problem

The README's `craft` pillar is the vaguest sketch of the six — one line:
"what is 'your space'? how does this compare with the market? what is our
trajectory along the way and why?" Nothing in `way` implements it; only
`Pillar::Craft` exists, as a label in test fixtures.

Gap-assessment surfaced that `craft`, for nick, isn't one thing — it's a set
of **disciplines** built and honed over long timescales, each at a
different stage: software engineering (active career — lead eng at Nike,
senior eng at Kong, senior eng/temporary team lead at ngrok), military
service and bridge engineering (13 years as SSG/PSG; not active, but not
necessarily closed either — a possible IRR reenlistment to finish the last
7 years toward 20 is a real, if uncertain, contingency), skateboarding
(actively being rebuilt — skating with his kids, mostly his youngest, at
least twice a week; real, current, trackable progress like landing 50-50
stalls), and woodworking (very early — more tools than experience so far,
a long-horizon hope rather than current practice).

The README's own "market" framing doesn't generalize across all four —
there's no "market" for skateboarding or woodworking the way there is for a
tech career — which surfaced the need for a broader shared concept.

## Solution

1. A single first-class entity, `Craft`, represents one discipline —
   mirroring how `relationships` unified children/partner into one `Person`
   entity rather than one type per relationship kind. `Craft` carries a
   `status` (`Active` | `Dormant` | `Historical`) rather than a simple
   active/archived flag: `Dormant` specifically captures something like
   military service — not currently practiced, but not permanently closed,
   contingent on something outside nick's control (unlike `Historical`,
   which is genuinely past with no realistic path back).
2. The README's "market comparison" question generalizes to a freeform
   `standing` field: where you currently stand relative to whatever the
   relevant comparison point actually is for that discipline — the job
   market for software engineering, personal skill progression or the
   local skate community for skateboarding, craftsmanship benchmarks for
   woodworking. Freeform, not structured — the comparison target varies too
   much across disciplines to force one shape (same reasoning already
   applied to `Person.preferences`).
3. `space` (freeform: what is your niche/focus within this discipline) and
   `trajectory` (freeform: direction of growth and why) round out the
   README's three questions as fields on `Craft`.
4. A `CraftSession` entity records a dated session log per craft —
   structurally identical to the body pillar's `RoutineCompletion` (a
   simple dated log entry with an optional note). Deliberately called a
   "session," not a "practice session": not every craft's logged time is
   practice in the drilling-a-rep sense — woodworking is building
   something, not rehearsing a move. This isn't a spin-off: nick explicitly
   named tracking/planning as a real, current need (skateboarding
   specifically), not an aside, and the shape is already a solved pattern
   from `RoutineCompletion` — reusing it is a small addition, not a new
   design problem.

## States

- `Craft.status`: `Active` (currently practiced/pursued), `Dormant` (not
  currently practiced, contingent on something outside nick's control —
  e.g. military service, pending IRR reenlistment politics), `Historical`
  (genuinely past, no realistic path back).
- A `Craft` can be deleted outright (rare, deliberate) — no archive state
  beyond what `status` already expresses; unlike `Routine`, `status` itself
  covers "not currently active," so a separate archived flag would be
  redundant.
- `CraftSession` is append-only, same as `RoutineCompletion` — logged, not
  edited after the fact.

## Behavior

- **Before**: no representation of disciplines/crafts in `way` at all.
- **After**: a craft can be defined (name, status, space, standing,
  trajectory) and refined over time as thinking about it changes — status
  can move (e.g. `Dormant` -> `Active` if military service resumes),
  `standing`/`trajectory` are expected to be edited as they evolve, not
  fixed at creation.
- **After**: a session can be logged against a craft (today, or a
  specific past date, with an optional note), and a craft's session history
  viewed reverse-chronological — same UX shape as `way routine log`/
  `way routine history`.

## Edge Cases

- Logging a session against a `Dormant` or `Historical` craft: allowed —
  logging is a historical fact independent of current status (e.g. logging
  a past bridge-engineering exercise), same reasoning as
  `RoutineCompletion` on an archived `Routine`.
- Logging the same craft more than once on the same day: allowed, no
  uniqueness constraint on (craft, date) — mirrors `RoutineCompletion`.
- A craft's `status` changes over time (e.g. `Dormant` -> `Active`): no
  history of past status values is kept in this MVP — only the current
  status. Status-change history is a reasonable fast-follow, not required
  to answer "what's my current relationship to this discipline."

## Observability

N/A — single-user local tool, no logging/metrics infrastructure, matches
existing precedent.

## Scope & Non-Goals

**in scope:**
- `Craft` entity: `name`, `status`, `space`, `standing`, `trajectory`
- `CraftSession` entity: dated session log per craft, optional note
- CLI CRUD for both

**out of scope:**
- Structured skill/progression tracking beyond freeform `standing`/`trajectory`
  text and the session log (e.g. a formal skill-tree, milestone system) —
  freeform is sufficient to answer the README's actual questions; more
  structure is speculative beyond what's been asked for
- Status-change history (when did this move from `Dormant` to `Active`) —
  only current status is tracked in this MVP
- TUI display/editing — CLI-first satisfies this PRD; any TUI work is
  provisional pending the [UX track](https://github.com/iamnande/way/issues/21)
- Search over crafts/sessions — low record count (a handful of disciplines),
  same reasoning as `Person`; revisit only via
  [comprehensive search](https://github.com/iamnande/way/issues/27) if that
  changes

## Design Decisions Summary

| decision | options considered | chosen | rationale |
|---|---|---|---|
| entity shape | one type per discipline vs. shared `Craft` entity | shared `Craft` | all four named disciplines answer the same three README questions in the same shape, differing only in content and current intensity |
| status model | simple active/archived flag vs. `Active`/`Dormant`/`Historical` | three-value status | military service specifically needs a "not active, but not closed" state — contingent on something outside nick's control, distinct from something genuinely finished |
| market-comparison field | keep as-is (market-specific) vs. generalize | generalized to freeform `standing` | "market" doesn't apply to skateboarding/woodworking; a freeform field capturing "where you stand relative to whatever's relevant" covers all four without forcing a career-specific shape onto hobby disciplines |
| session log | spin out as separate ticket (like body's sleep/medical) vs. include in this steel thread | include | structurally identical to the already-solved `RoutineCompletion` pattern, and nick named it as a real current need (skateboarding), not an aside — small addition, not a new design problem |
| session terminology | "practice session" vs. "session" | "session" | woodworking's logged time is building something, not drilling a rep — "practice" doesn't fit every craft the log needs to cover |

## Requirements

- **R1:** `way` supports a `Craft` entity (`id`, `name`, `status`, `space`,
  `standing`, `trajectory`), independent of `Task`.
- **R2:** `way craft add <name> --status <active|dormant|historical>`
  creates a craft; `space`/`standing`/`trajectory` are optional at creation
  and editable afterward.
- **R3:** `way craft list [--status <...>]` / `way craft show <name>` list
  crafts (optionally filtered by status) / show one in full.
- **R4:** A craft's `status`/`space`/`standing`/`trajectory` can each be
  updated independently via the CLI.
- **R5:** `way craft remove <name>` deletes a craft outright (no archive
  state — `status` already covers "not currently active").
- **R6:** `way` supports a `CraftSession` entity (`id`, `craft_name`,
  `logged_on`, optional `note`), persisted independently of `Craft`.
- **R7:** `way craft log <name> [--date] [--note]` records a session;
  `way craft history <name>` lists a craft's sessions
  reverse-chronological. Logging never requires the referenced craft to be
  `Active`.
- **R8:** All of the above is reachable non-interactively via the CLI
  (CLI-first convention).
